# Импорт типов сторонних библиотек в IDA Pro через Parse C Header

## Контекст задачи

При анализе PE-файла в IDA вы видите вызовы функций вроде:

```
.text:0040227B    call    SDL_CreateTextureFromSurface
```

IDA знает имя функции (из таблицы импортов), но не знает её сигнатуру — количество аргументов, их типы, возвращаемое значение. Декомпилятор Hex-Rays в таком случае покажет что-то вроде `sub_40227B(v1, v2)` без каких-либо типов. Чтобы это исправить, нужно загрузить в IDA описание типов из заголовочных файлов библиотеки.

---

## Почему заголовочные файлы, а не DLL

Первый инстинкт — взять `SDL2.dll` и вытащить из неё всё что нужно. Это не сработает по фундаментальной причине: **DLL содержит только имена экспортируемых символов, но не типы их аргументов**. Информация о типах существует исключительно в заголовочных файлах (`.h`), которые используются при компиляции. После компиляции она теряется — в машинном коде нет никаких типов, только инструкции и адреса.

Файл `.til` (Type Information Library), который IDA создаёт сама рядом с проектом (`Magic8Ball.exe.til`), тоже не подходит: он содержит типы, которые IDA смогла вывести самостоятельно из анализа бинаря, а не полные описания из SDK.

---

## Механизм Parse C Header

`File → Load file → Parse C header file` запускает встроенный C-парсер IDA. Он читает указанный `.h` файл, разворачивает все `#include`, вычисляет все `typedef`, `struct`, `enum` и функциональные прототипы, и добавляет результат в локальную базу типов проекта (`Local Types`). После этого Hex-Rays автоматически применяет найденные прототипы к соответствующим импортируемым функциям.

Парсер — это не полноценный компилятор. Он не производит машинный код и не линкует ничего. Его единственная задача — понять объявления типов. Поэтому ему всё равно нужна полная цепочка `#include` вплоть до системных заголовков, иначе он не поймёт что такое `size_t`, `uint32_t` и прочие базовые типы.

## Почему возникают проблемы на практике

### Проблема 1: отсутствие системных заголовков

`SDL.h` включает `SDL_stdinc.h`, который включает стандартный `stddef.h`. Этот файл не входит в SDL2 — он часть компилятора или SDK операционной системы. Без него парсер сразу падает с `Can't open include file 'stddef.h'`.

**Решение:** указать путь к системным заголовкам в `Options → Compiler → Include directories`. На Windows это два пути:
- Заголовки MSVC runtime: `C:\Program Files\Microsoft Visual Studio\...\VC\Tools\MSVC\...\include`
- Заголовки Windows SDK (UCRT): `C:\Program Files (x86)\Windows Kits\10\Include\ucrt`

Оба нужны потому что стандартная библиотека C в Windows разделена: часть определений живёт в MSVC (`type_traits`, C++-специфика), часть — в UCRT (`stdio.h`, `stddef.h`, POSIX-совместимые вещи).

### Проблема 2: архитектура и платформа

Заголовочные файлы содержат `#ifdef`-блоки, которые выбирают разные ветки кода в зависимости от целевой платформы и архитектуры. Если парсер не знает что он разбирает Windows x86 PE, он пойдёт в неправильные ветки и получит ошибки.

Это управляется через **Predefined macros** — набор макросов, которые "предопределены" до начала парсинга, как если бы они были переданы компилятору через флаг `-D`.

Для Windows x86 PE нужно минимально определить:
- `_WIN32` — стандартный макрос, означающий что цель — Windows (32 или 64 бит)
- `_M_IX86` — макрос MSVC, означающий x86 (32-битная архитектура)

Без них заголовки попытаются определить платформу по окружению парсера (в нашем случае — ARM Mac или ARM Windows), получат неверный результат и упадут с `#error Unsupported architecture`.

### Проблема 3: Source parser и передача макросов

В IDA есть несколько встроенных C-парсеров: `legacy` (старый собственный парсер IDA), `clang` (LLVM Clang), `old clang`. Они отличаются поддерживаемым синтаксисом и способом передачи параметров.

**Критически важный момент:** поле `Predefined macros` в `Options → Compiler` работает только с парсером `legacy`. Когда выбран `clang`, это поле неактивно и игнорируется. Макросы для clang передаются через поле **Arguments** в формате флагов командной строки:

```
-D_WIN32 -D_M_IX86 -D__PRFCHWINTRIN_H
```

Это стандартный синтаксис Clang/GCC: `-DNAME` определяет макрос `NAME` со значением `1`, `-DNAME=VALUE` определяет макрос с конкретным значением, `-DNAME=` определяет пустой макрос (эффективно "заглушает" его).

### Проблема 4: конфликт builtin-функций

В `SDL_endian.h` есть такой блок:

```c
#if defined(_MSC_VER) && (_MSC_VER >= 1400)
#ifdef __clang__
#ifndef __PRFCHWINTRIN_H
#define __PRFCHWINTRIN_H
static __inline__ void __attribute__((__always_inline__, __nodebug__))
_m_prefetch(void *__P) { ... }
#endif
#endif
#include <intrin.h>
#endif
```

Логика этого блока: авторы SDL2 знали, что в Clang есть конфликт между собственным объявлением `_m_prefetch` и тем, что приходит из `winnt.h` через `intrin.h`. Поэтому они добавили заглушку — объявляют `_m_prefetch` сами, через guard `__PRFCHWINTRIN_H`, до того как подключится `intrin.h`.

Проблема в том, что IDA с парсером `clang` одновременно определяет и `_MSC_VER` (потому что выбран компилятор Visual C++ в настройках) и `__clang__` (потому что парсер — Clang). SDL2 попадает в этот блок, пытается объявить `_m_prefetch` как статическую inline-функцию с атрибутами GCC, и парсер IDA падает, потому что не может переопределить встроенную функцию таким образом.

**Решение:** передать макрос `-D__PRFCHWINTRIN_H` в Arguments. Это активирует guard `#ifndef __PRFCHWINTRIN_H` — условие становится ложным, весь проблемный блок пропускается, конфликта не возникает.

## Итоговый алгоритм

**Шаг 1. Определить библиотеку**

Открыть `View → Open subviews → Imports`. Найти DLL которые импортирует бинарь. В данном случае `SDL2.dll` — значит нужен SDL2 SDK.

**Шаг 2. Получить заголовочные файлы**

Скачать исходники SDL2 с GitHub releases (`SDL-release-X.X.X.zip` или `.tar.gz`). Нужна только папка `include/` — в ней все `.h` файлы.

**Шаг 3. Установить компилятор с системными заголовками**

Установить Visual Studio (Community достаточно) с компонентами:
- `MSVC Build Tools for x64/x86` — даёт заголовки MSVC runtime
- `Windows 11 SDK` — даёт заголовки UCRT (`stddef.h`, `stdio.h` и т.д.)

**Шаг 4. Настроить Options → Compiler**

| Параметр | Значение |
|---|---|
| Compiler | Visual C++ |
| Source parser | clang |
| Include directories | `путь\к\MSVC\include;путь\к\Windows Kits\ucrt` |
| Arguments | `-D_WIN32 -D_M_IX86 -D__PRFCHWINTRIN_H` |

Поле Predefined macros при выбранном clang неактивно — все макросы идут через Arguments.

**Шаг 5. Запустить парсинг**

`File → Load file → Parse C header file` → выбрать `SDL.h` из папки `include/` SDL2.

**Шаг 6. Проверить результат**

`View → Open subviews → Local Types` — там должны появиться все типы SDL2: структуры, enum'ы, typedef'ы. Открыть функцию в Hex-Rays (F5) — аргументы `SDL_CreateTextureFromSurface` теперь должны отображаться с правильными типами.

## Общий принцип для произвольного PE

При анализе незнакомого PE алгоритм определения нужных заголовков:

1. **Смотреть Imports** — какие DLL импортирует бинарь. Каждая сторонняя DLL означает сторонний SDK.
2. **Определить компилятор** — по runtime DLL (`MSVCP140.dll` → MSVC, `libgcc` → MinGW) выбрать соответствующий компилятор в настройках IDA.
3. **Скачать dev-пакеты** — для каждой сторонней библиотеки найти её официальный SDK или исходники с заголовками.
4. **Настроить макросы под цель** — `_WIN32`/`_WIN64` для Windows, `_M_IX86`/`_M_X64`/`_M_ARM64` для архитектуры.
5. **Парсить минимально необходимое** — если нужна одна функция из большой библиотеки, иногда проще спарсить только один конкретный `.h` файл, а не весь SDK.
